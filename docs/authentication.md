# Authentication flow

Import lines are `account----password----totp_secret[----mailbox_url]`; the fourth field is a mailbox URL, never a proxy. Preview checks in-file and existing case-insensitive identities. Confirmation rejects any invalid row and commits all records atomically. Imported accounts start without a route or binding; choose direct/proxy and bind a target before starting a task. Optional TOTP seeds must decode as base32 with at least ten bytes. HTTPS mailbox URLs are the default; HTTP requires explicit account configuration. Local/private mailbox literals and unsafe schemes are rejected.

OpenAI's adapter launches a headed browser in the worker's virtual screen. Visible editable inputs and active form instructions identify email, password, TOTP, email-code, generic-code and consent steps. Readonly or disabled transition inputs are skipped. Alternative-method links and buttons do not establish the active code source. Unknown, CAPTCHA, third-party and device steps pause for manual review instead of repeated clicking. TOTP waits for at least five seconds of validity, attempts at most two distinct windows, then pauses. Password submission is not blindly repeated. Account identity must match the imported username before any result is accepted.

With the default `cpa-auth-files-v1` target, Codex uses generated state and PKCE S256, exact localhost callback interception, and one bounded code exchange through the account route. Invalid/duplicate callback parameters fail; uncertain exchanges are not replayed. ChatGPT Web uses the browser-context session endpoint and checks session email, token and expiry. Maintenance reuses only an existing authenticated session; absence/expiry becomes `reauth_required` and requires administrator-triggered login.

Opt-in `cpa-native-oauth-v1` requires the patched CLIProxyAPI management extension. The app still automates the same login browser and offers manual takeover; the target generates the authorization URL and PKCE state and performs the code exchange through the account route. The bridge intercepts the callback and submits it once to that authenticated extension. Tokens remain staged at the target until a separately fenced commit; the bridge stores only an encrypted native-session reference and submission marker. It does not silently fall back to local token exchange or replay an uncertain callback. See [native contract](integrations.md#cliproxyapi-native-oauth-extension).

## Routing and isolation

Direct is explicit: httpx ignores environment proxy settings and Chromium uses no proxy. HTTP, HTTPS and authenticated SOCKS5 use GOST 3.3.1 as a local HTTP bridge for both Chromium and token exchange. Upstream credentials live only in a restricted temporary config, never process arguments or logs. A failed proxy fails the task. TLS proxy certificates are verified. Chromium disables nonproxied WebRTC UDP, background networking and service workers. The local callback is intercepted before network access. Each run uses a new context and closes it on termination. One encrypted browser identity and saved browser session belong to each local account, shared across its Voice and Codex tasks. The worker creates the identity before first navigation and retains it after failed logins, retries, restarts, and password, proxy, username or target changes. Existing saved sessions are preserved by migration; no persistent plaintext profile is used.

The identity uses supported native context options: a stable per-account viewport/screen choice, `en-US` locale, UTC timezone, scale 1, light color scheme, no motion preference, no forced colors, desktop mode and no touch. Deleting an account removes its identity; recreating it generates a new one. Chromium supplies its real user agent/version. No JavaScript stealth patches or fabricated provider device ID are used. These controlled settings do not provide comprehensive Canvas, WebGL, font, audio or hardware fingerprint isolation, nor guarantee globally unique fingerprints. A changed route still uses the new explicit route. Real-account login, cross-target session reuse and actual egress remain unverified. The production browser enables the Chromium sandbox; container sandbox runtime acceptance remains unverified.

## Webmail boundary

No site-specific webmail adapter is enabled because no test mailbox/deployed site contract was supplied. `app/mailbox.py` supplies public-address URL checks and conservative fresh-message selection by baseline ID, sender, recipient, purpose and timestamp. Ambiguous messages return no code. These are extension primitives, **not an implemented generic mail reader**. DNS validation alone does not prevent rebinding; a future automatic adapter must also pin resolved addresses or enforce egress filtering across every redirect. Do not enable arbitrary mailbox navigation without that boundary.

At present, email-code challenges offer code entry and same-session provider takeover. The configured mailbox URL is encrypted and is not navigated automatically. Automatic mail polling, isolated mailbox browser operation and a real site's redirect/list/detail contract remain pending serial real-account acceptance. No mailbox content is saved.

## Human operation

Task actions submit a code, request takeover, continue, cancel or retry sync. Starting takeover pauses automation at the next bounded checkpoint. The dedicated noVNC window uses the authenticated app WebSocket path, checks Origin, and binds access to the live waiting task. Continue closes that access and re-identifies the page. Cancellation closes the browser. Waiting expires after thirty minutes, producing an interrupted task that can be restarted. OTP commands are encrypted, omitted from logs, and cleared when consumed.

Manual pauses expose code entry for recognized email, authenticator, and generic verification code challenges. SMS or ambiguous instructions use `verification_code_required` and accept a manually supplied code; only explicit authenticator instructions permit automatic use of the saved TOTP seed. A password form that remains after automatic submission instead asks the administrator to inspect the password/provider error through takeover and continue. The adapter classifies the current page on every iteration; email entry is optional, and a direct password page, a code challenge, or an existing authenticated session bypasses earlier steps. After email/login/consent submission or on an unknown intermediate page, it keeps checking for up to 30 seconds so delayed navigation or SPA rendering can expose the next challenge. Password/code forms retain a four-second settling window, and automation does not repeat a password submission. Unknown pages that outlast the transition window still require takeover. If takeover changes the page while a code is pending, the adapter discards that code and identifies the current page again. These behaviors are covered with synthetic provider pages; real-account verification remains unverified.
