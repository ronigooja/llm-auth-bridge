# Fixed login workflow and account window

The account row offers two login actions. **登录 ChatGPT** submits `POST /api/v1/accounts/{id}/login-flow` with `voice_target_id` and an idempotency key, omitting `cli_target_id`. It logs in and synchronizes ChatGPT Web Voice and works without a bound CLIProxyAPI target.

**登录 Codex** submits the same endpoint with both `voice_target_id` and `cli_target_id`. It checks the saved ChatGPT Web session, logs in if needed, then authorizes Codex through CLIProxyAPI. The backend reuses a valid saved Web session and owns the durable dependency: CLI execution starts only after Voice synchronization succeeds. The UI never starts the second task itself. Task details display `depends_on_task_id` when present.

Only targets bound to the account appear. A single target of each relevant kind is selected automatically. Multiple targets require an explicit selection. ChatGPT mode shows and requires only the Voice selector; Codex mode shows and requires both selectors. Missing required targets disable submission and direct the operator to edit account bindings. New account forms initially select supported targets, with visible checkboxes for editing bindings.

The account row and task details expose the same **账号窗口** action. The app reserves one large, resizable same-origin popup during the click, then calls `POST /api/v1/accounts/{id}/browser`. This endpoint reuses the current account task or queues an idle `browser_window` task. A blocked popup does not queue work. Opening another account while the popup remains open requires first closing the current window, so one account is never silently substituted for another.

The viewer keeps polling through `sync_pending` and displays a synchronization status while the browser is unavailable. When a login task succeeds, an open popup queries the task list and automatically follows an active dependent task for the same account. This carries the viewer from ChatGPT session preparation to Codex authorization without creating an idle browser. Clicking **账号窗口** again for an ended task explicitly rebinds the existing popup through the account browser endpoint; an active task simply receives focus.

The popup embeds the same-origin noVNC viewer. Running automation uses `/api/v1/tasks/{id}/monitor`, `view_only=true`, and `shared=true`, and opening the viewer does not pause automation. **接管** explicitly requests takeover, then waits for the task API to confirm `waiting_human` before switching to the interactive `/takeover` path. The operator resumes login from the task page with **继续任务**.

An idle browser task becomes interactive when it reaches `waiting_human`. Close the popup with its native **×** control when finished; there are no additional save or hide buttons in the popup or idle-task controls. Closing automatically releases an idle browser session through `continue`; if the task is still queued, the controller waits until it is ready. The controller polls until the worker confirms completion, and terminal failures remain visible with the server-provided safe failure message on the management page and popup, without claiming persistence succeeded. After a failed close response, it reconciles task status before retrying, including when the server accepted the request but its response was lost. An unfinished idle session blocks switching accounts until it ends and can be reopened while waiting. Closing a live login viewer only closes the viewer and does not continue or cancel its task. The popup explains these close behaviors; **接管** remains available, and automated login resumes only through **继续任务** on the task page. The controller remains mounted across management page navigation and polls the task every second while active.

The native-close cleanup depends on the management page remaining open. Refreshing or closing the entire management page, signing out, or losing its network connection can leave the idle session active until backend recovery or timeout. Reopen the same account window after reconnecting to recover, then close the popup to finish the session. Browser state persistence is performed by the backend, not the viewer.

Real-account provider login, persistence, live noVNC interaction, and popup behavior across production browser policies remain unverified until serial real-account acceptance. Synthetic frontend tests cover endpoint contracts, target selection, monitor-to-takeover gating, native popup closure, delayed readiness, close-response loss and recovery, and blocked popups.
